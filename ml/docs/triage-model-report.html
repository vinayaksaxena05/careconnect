Predicting Emergency Severity Index acuity as triage decision support

triage_model_v1 takes the eleven things a nurse records at the initial emergency triage assessment and returns a suggested ESI acuity of 1–5, with a calibrated-in explanation and a permanent seat behind a human reviewer. This report describes the data, the model, the selection procedure, the measured behaviour, and the engineering choices that keep the prediction subordinate to clinical judgement.

Abstract

Emergency-department triage assigns each arrival an Emergency Severity Index (ESI) acuity from 1 (resuscitation) to 5 (non-urgent). We frame acuity assignment as a five-class prediction problem constrained to information available at the moment of triage — demographics, arrival mode, the first set of vital signs, a pain score, and the free-text chief complaint — with a documented per-column leakage policy that excludes everything recorded after the triage decision.

A four-family model zoo (logistic regression, decision tree, random forest, XGBoost), each evaluated with and without a TF‑IDF representation of the chief complaint, is compared on a held-out validation split using macro‑F1 with a high‑acuity‑recall tie‑break. XGBoost with free text wins (validation macro‑F1 0.709) and is refit on train + val and scored once on an untouched test split: accuracy 0.793, macro‑F1 0.738, and — the number that matters — recall 0.846 / precision 0.943 on the combined ESI 1–2 “must not miss” group.

The contribution is less a model than a discipline: the entire inference path (feature engineering, imputation, encoding, text vectorisation, estimator) is serialised as one object so training and serving cannot diverge; a single config module is the shared contract for preprocessing, the API schema, and the UI; a transparent rule-based predictor stands behind the model on the same response contract so the endpoint degrades instead of failing; and model output and human decision are stored side by side, the model columns immutable.

§1

Background: what triage has to decide, in under five minutes

Every patient who walks or is wheeled into an emergency department is sorted before they are treated. The dominant instrument in North American EDs is the Emergency Severity Index, a five-level scale that blends how sick with how many resources the patient is likely to need.

1Resuscitation
2Emergent
3Urgent
4Less Urgent
5Non‑Urgent

The assignment is fast, high-consequence, and known to vary between nurses and shifts, especially in the crowded middle of the scale. That makes triage a textbook case for decision support: a second opinion computed from the same inputs, surfaced at the same moment, that a clinician can take or leave. It is emphatically not a case for automation — a wrong ESI entered silently is a patient in the wrong queue.

triage_model_v1 is built for that narrow role. It reproduces the nurse’s inputs, predicts the acuity a nurse would assign, shows why, and hands the decision back. Nothing downstream in CareConnect reads the model’s number; only a human’s recorded ESI moves a patient.

§2

Problem definition and the leakage horizon

The prediction target is esi ∈ {1,2,3,4,5}, the acuity a triage nurse assigned (triage.acuity in MIMIC‑IV‑ED). Classes are not collapsed: a model that folds 1–2 together cannot tell a resuscitation from an emergency. Instead, ESI 1–2 is carried through evaluation as a separate one-vs-rest “high acuity” problem, because missing those patients is the costliest error the model can make.

Every feature must be knowable before the triage decision. The single hardest discipline in a clinical prediction is refusing the features that quietly encode the outcome — diagnosis, disposition, ICU transfer, mortality, length of stay, medications given, later vitals and notes. All of these live on the wrong side of the line below and are never read from any table.

§3

Data: a credentialed target and a synthetic stand-in

The intended training corpus is MIMIC‑IV‑ED (PhysioNet), joining the edstays arrival record to the triage observation row, with the optional patients table supplying age. MIMIC is credentialed and never enters the repository; the loader (ml/data/mimic.py) is complete and unit-tested but unexercised here.

So the pipeline can run end to end — and the API can serve a real model — triage_model_v1 is trained on a reproducible synthetic dataset with the identical schema and column semantics. The generator (ml/data/synthetic.py) is a transparent hand-built scorecard: a latent severity band is sampled (ESI 3 dominates, ESI 1 is rare, matching real EDs); vitals are drawn from band-conditioned normals; a chief complaint is drawn from a band-appropriate phrase list with 12 % cross-contamination so text carries real but imperfect signal; ESI is then assigned from a blend of vital-sign danger, complaint red-flags, an age term, and irreducible noise. Realistic missingness is injected into temperature, respiratory rate, diastolic BP, pain, and SpO₂.

Consequence Synthetic data is not clinically valid. It exercises and demonstrates the machinery; it says nothing about how the model would triage a real patient. A MIMIC-trained v2 would differ, most visibly on ESI 4.

§4

Features and preprocessing as one serialised object

Eleven raw inputs feed the model: eight numeric (age, heart_rate, respiratory_rate, systolic_bp, diastolic_bp, oxygen_saturation, temperature, pain_level), two categorical (sex, arrival_transport), and the free-text chief_complaint. Two derived numerics are computed deterministically from the raw vitals: shock index (HR / SBP) and pulse pressure (SBP − DBP), both standard bedside danger signals.

Crucially, the preprocessing is not a script that runs before the model — it is the model. joblib.dump serialises a single scikit-learn Pipeline whose first step engineers features, whose second is a ColumnTransformer doing imputation / scaling / one-hot / TF‑IDF, and whose third is the estimator. Inference calls predict_proba on that one object. There is no second code path to keep in sync.

Out-of-range physiological values are treated as recording errors: clipped to NaN by the engineer, then imputed — never silently dropped. Unknown categorical values fold to an unknown level; OneHotEncoder(handle_unknown="ignore") means a novel arrival mode at inference does not raise.

§5

Model family and a selection procedure tied to clinical cost

Four estimator families are trained: logistic regression, a depth-limited decision tree, a 300-tree random forest — the three scikit-learn families all with balanced class weights — and an XGBoost classifier (multi:softprob, 400 trees, depth 5, learning rate 0.05, subsample and column-sample 0.9). Each is fit twice: on the structured features alone, and on the structured features plus the TF‑IDF chief complaint.

Selection never uses accuracy. On the ESI distribution, a model that always says “3” scores well on accuracy and is clinically useless. The criterion is macro‑F1 on the validation split, with high‑acuity (ESI 1–2) recall as the tie-break.

After selection the winner is cloned, refit on train + val (9,600 rows), and scored exactly once on the test split. Training refuses to overwrite an existing model version without --force, writes {model_name, version, dataset, seed, split sizes, library versions, metrics, comparisons, disclaimer} alongside the .joblib, and updates models/latest.json so the server picks up the new version on restart.

§6

The free-text component

The chief complaint enters as one TfidfVectorizer step: unigrams and bigrams, sublinear term frequency, English stop words, min_df = 2, capped at 400 features. It is a single pipeline node — replaceable with embeddings without touching anything outside the artifact.

Its value is measured, not assumed. For the winning family the run records structured-only versus structured-plus-text on the validation split:

§8

Explanations that never break inference

Every prediction carries an explanation. For the ML predictor it is a SHAP TreeExplainer (with a LinearExplainer fallback) run on the transformed row for the predicted class. The many transformed columns — each one-hot level, each TF‑IDF term — are folded back onto their source feature, so the output speaks in clinical terms: “oxygen saturation”, “chief complaint”, “shock index”. The top five drivers are returned as {feature, label, impact, importance}, where impact is increased_acuity / decreased_acuity / neutral, interpreted against the fact that ESI is ordinal with 1 as most acute.

Design rule Explanations are best-effort. Any failure — a SHAP version mismatch, an unexpected shape — returns an empty method:"none" block. A prediction is never lost because its explanation could not be produced. The rule-based fallback emits the same structure with method:"heuristic", listing the thresholds that fired.

The disclaimer travels in the payload: the explanation “describes how the model weighted the inputs for this prediction. It is not a clinical assessment.”

§9

Serving architecture and the safety envelope

The model is loaded once, at FastAPI startup, and held in memory by a process-wide TriageService. A missing or corrupt artifact never crashes the app: build_predictor falls back to a transparent rule-based predictor (auto mode), or the endpoints return a controlled 503 and manual triage simply continues.

Input validation is strict: age 0–120; each vital inside a physiological range; categorical values normalised to fixed vocabularies; unknown request fields rejected; and at least 3 of 6 core vitals required, so a near-empty form cannot elicit a confident answer. Range or shape violations return 422. Raw patient data is never written to the application log — only the failure class.

§10

Contributions

The estimator is stock. What is deliberate here is the set of constraints that keep a probabilistic model safe to put in front of a triage nurse, and reproducible enough to retrain against real data without touching the product.

  1. The artifact is the entire inference path. Feature engineering, imputation, encoding, and text vectorisation are pipeline steps inside the serialised object, not preprocessing that has to be re-implemented at serving time. Train / serve skew is ruled out by construction rather than by test.
  2. One config module is the shared contract. Feature names, physiological ranges, the ESI label map, and the minimum-vitals rule live in ml/config.py and are imported by preprocessing, training, the Pydantic API schema, and (mirrored) the UI. The model, the endpoint, and the form cannot drift apart silently.
  3. Selection is aligned to clinical cost, not accuracy. Macro‑F1 with a high‑acuity‑recall tie‑break; ESI 1–2 carried through as a separate one-vs-rest evaluation; accuracy reported but never optimised.
  4. Structured and free text are fused in one swappable step, and the text’s contribution is measured every run (structured vs structured + TF‑IDF) and stored in the artifact metadata — an ablation you cannot forget to do.
  5. A transparent fallback shares the response contract. The rule-based predictor is not machine learning and says so in its output, but it satisfies the same interface, so the endpoint degrades to “coarse but working” instead of “down”.
  6. “Decision support, never decision” is enforced end to end. requires_human_review is always true; the clinical notice is in every payload; the model and human ESI are stored side by side with the model columns immutable; and the UI visually subordinates the model card to the human decision.
  7. Explainability that cannot break a prediction, and that reports in clinical features by folding encoded columns back to their source, with impact direction interpreted on the ordinal ESI scale.
  8. Reproducible, hot-swappable versioning. Every artifact ships metadata with seed, split sizes, library versions, and full model / text comparisons; models/latest.json repoints the server; a new --model-version requires no API or UI change. The synthetic generator mirrors the real schema so the whole pipeline is runnable with no credentialed data.
§11

Limitations and ethics

  • Synthetic training data. triage_model_v1 is a pipeline and integration demonstration. It must not be deployed for real triage. Its metrics describe the synthetic generator as much as the model.
  • ESI 4 is under-recalled (0.25). The synthetic ESI 4 band is narrow and sits between well-separated neighbours, so the model routes it to 3 or 5. A MIMIC-trained model would behave differently; until then, a predicted “4” deserves extra scrutiny.
  • Probabilities are uncalibrated. confidence is simply the top-class probability; it is not a calibrated likelihood and should not be read as one.
  • No fairness or subgroup analysis, no temporal validation. A clinical deployment would require both, plus prospective silent-mode evaluation.
  • A single snapshot. The model sees one triage assessment. It does not reassess, and it has no notion of trajectory or deterioration.
  • Automation bias is a real risk of decision support. The mitigations here — mandatory review, an un-authoritative UI, stored overrides, an explicit notice — reduce but do not eliminate it. The stored model-vs-human record exists partly so that drift toward rubber-stamping can be audited.
  • MIMIC caveat. age is absent from MIMIC‑IV‑ED unless the patients table is also supplied; without it that feature is imputed and contributes nothing.
